# SOP 审查准则

以被审任务绑定的规则为准。先读 `00-overview.md` 的版本、规则路径、Profile、流程及任务状态。当前 Wally 读取绑定版本 Core 的 `workflow.md` 和 `gates.md`、项目 `.wally/profiles/project.md`、`.wally/review.md` 以及任务 `execution.json`（历史任务如自带 `profile.md` / `_rules/review.md` 兼容读取）。按相关性读取项目架构、接口、数据、测试、部署文档，通常在 `.wally/docs/` 或项目 `docs/`。规则路径缺失或冲突时留下证据缺口，不能用新模板追溯判定历史任务。只读取仓库或用户授权范围内的引用。

## 布局与门禁

- `.wally` 六步 SOP 审查 `00-overview.md`、`01-clarify.md`、`02-plan.md`、`03-implement.md`、`04-deploy.md`、`05-it.md`。03 包含实现、UT、增量覆盖率、Docs、增量 CR；按标题与绑定规则定位，兼容中英文及章节改版。
- 历史四步任务审查 `00` 到 `03`，Deploy/IT 不适用。使用 Meta 与步骤文件名交叉识别四步或六步；布局无法归入这两种时，记录 SOP 判定缺口。只有明确要求时才审末步 Review/Commit。03 的增量 CR 仍在范围内。
- 当前 `.wally` 六步分别查看 `execution.json` 中 `deploy` 和 `it` 的 `command` 与 `guide`。两者对某步骤都为空时，按绑定规则核对是否留存 `SKIPPED`、原因、时间及未验证范围。零耗时可对应跳过决定。已配置却缺权限、缺工具、缺环境或执行失败，按真实状态记录为失败或阻塞。历史任务按各自版本的跳过规则判断。

## 核查证据

- **任务状态与授权**：核对分支、目标、状态、步骤和时间线。工单、分支前缀、阶段确认或例外批准仅在绑定规则有要求时作为门禁。未到阶段的待办按阶段标记，交付前或合并前应存在的证据才作为该次门禁。核对关键步骤与授权时点；单凭时间缺失或顺序异常只能报告缺口，不能断言事后补录。
- **澄清与方案**：把验收项映射到设计、文件、测试与交付证据。核对调用链、API 与数据迁移、旧数据和客户端、灰度、回滚及失败边界；仅在和变更有关时检查相应风险。对关键逻辑比对前置校验、运行条件和最终结果，沿正常、边界及失败路径验证是否一致。
- **实现、UT 与增量 CR**：核对方案偏差及其批准或记录、TDD/回归证据、测试命令和关键断言。需要覆盖率时确认指标是当前版本的增量覆盖率，阈值取自任务规则。核对增量 CR 的必要检查、未处理问题与关闭证据；自审通过不能替代当前独立代码检查。
- **Deploy/IT**：核对实际环境、执行版本、命令或任务、逐条验收结果、可追溯的日志或运行标识及回滚要求。区分断言、执行与环境失败。验证后改过核心逻辑时，确认旧证据仍能覆盖最终行为，否则指出受影响路径。跳过不视为环境验证通过。
- **Docs**：检查架构、配置、API、数据、测试或运维契约变更是否有对应更新，并核对文档与实现。有合理且可验证的不影响说明时可记为不适用。
